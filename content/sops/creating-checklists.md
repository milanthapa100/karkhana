## Description

This SOP explains how unit members should create simple work checklists after completing tasks. The purpose is to record real work clearly so that tasks can be repeated, reviewed, improved, and later converted into full SOPs when needed.

A checklist is not a full SOP. A checklist is the first simple record of how work is done.

## When This SOP Is Used

Use this SOP when:

- A person completes a task and needs to record how it was done
- A task is repeated often
- A task has steps that are easy to forget
- Another person may need to learn the task
- A task needs proof of completion
- The team is deciding whether a task should become a full SOP

## Roles and Responsibilities

| Role | Responsibility |
|---|---|
| Work Owner | Creates the first checklist based on work they actually do |
| Peer Reviewer | Checks whether the checklist is clear and usable |
| Unit Lead | Decides whether the checklist should remain a checklist or become an SOP |
| SOP Coordinator | Maintains checklist naming, location, version, and tracker entry |

## Inputs Needed Before Starting

Before creating a checklist, the Work Owner should have:

- A task they have completed at least once
- The real steps they followed
- Required files, folders, links, tools, or trackers
- Known problems or confusing points
- The expected output of the task
- Any proof that shows the task is complete

## Steps

### Step 1: Choose One Clear Task

Select one specific task to document.

Good checklist topics:

- Lesson Folder Setup
- Weekly Log Filling
- Video Review
- QR Tracker Update
- Book Export Check

Avoid combining many tasks into one checklist. If the checklist becomes too broad, split it into smaller checklists.

### Step 2: Fill the Checklist Header

Every checklist must include:

- Task name
- Unit
- Work owner
- Date created
- Version (use v0.1 for the first draft)

### Step 3: Write the Trigger

Write when the checklist should be used. Use this format:

> I use this checklist when [situation happens].

### Step 4: List What Must Be Ready Before Starting

Write the inputs needed before the work begins. Include files, folders, links, tools, tracker access, information needed, and person to contact if something is missing.

### Step 5: Write the Work Steps in Real Order

Write the steps in the same order the work is actually done.

Rules:

- Start each step with an action verb
- Keep each step short
- Write only one action per line
- Avoid long explanations
- Avoid vague words like "properly", "manage", or "check everything"

Useful action verbs: Open, Check, Create, Update, Add, Compare, Review, Export, Share, Inform

### Step 6: Add Quality Checks

Add checks that confirm whether the work is done correctly. Quality checks must be visible or provable.

### Step 7: Define the Output

Write what should exist after the checklist is completed. Outputs may include completed folder, updated tracker, exported PDF, review note, final file, handover message, or remarks for missing items.

### Step 8: Add Problem and Improvement Space

Every checklist should leave space for learning from real work.

| Problem | What I Did | Support Needed |
|---|---|---|
| [Problem] | [Action taken] | [Help needed] |

Also add:

- What should improve next time?
- What was confusing?
- What support is needed?

### Step 9: Review the Checklist

Before sharing, the Work Owner checks:

- The checklist is short enough to use while working
- The trigger is clear
- Inputs are listed
- Steps are in the correct order
- Each step starts with an action verb
- Quality checks are specific
- Output is clear
- Problems and improvements can be recorded

### Step 10: Peer Test the Checklist

Give the checklist to another person and ask them to follow it or review it. The Peer Reviewer checks:

- Can I understand when to use this?
- Can I complete the work using this checklist?
- Do I know what files, links, tools, or trackers are needed?
- Do I know what "done" means?
- Do I know what to do if something is missing?

### Step 11: Decide the Checklist Status

After review, choose one status: Draft, In Use, Needs Review, Ready for SOP, or Archived.

| Decision | When To Choose It |
|---|---|
| Keep as checklist | Task is simple, personal, or temporary |
| Use 2-3 more times | Task is still changing or unclear |
| Convert into SOP | Task is repeated, important, shared, or affects quality |

### Step 12: Save and Track the Checklist

After the checklist is ready:

1. Save it in the correct checklist folder
2. Add the checklist to the tracker
3. Add the owner, version, status, and last updated date
4. Link it to related SOPs if needed
5. Inform the people who need to use it

## Checklist Format

Use this format when creating a new checklist:

```
Task Name: [Write task name]
Unit: [Write unit]
Work Owner: [Write role or name]
Date Created: [Date]
Version: v0.1

1. When Do I Use This Checklist?
   I use this checklist when [write trigger].

2. What Should Be Ready Before I Start?
   - [Input 1]
   - [Input 2]

3. What Steps Do I Follow?
   - Step 1:
   - Step 2:

4. What Should I Check Before It Is Done?
   - [Quality check 1]
   - [Quality check 2]

5. What Output Should Exist?
   - [Output 1]
   - [Output 2]

6. What Problems Did I Face?
   | Problem | What I Did | Support Needed |
   |---|---|---|

7. What Should Improve Next Time?
   - [Improvement 1]
   - [Improvement 2]

8. Should This Become an SOP?
   - Keep as checklist
   - Use 2-3 more times before deciding
   - Convert into SOP
```

## Common Mistakes

- Writing the checklist before doing the actual work
- Writing a checklist like a long explanation
- Mixing many tasks into one checklist
- Forgetting to write when the checklist should be used
- Forgetting inputs and access requirements
- Writing vague steps
- Not defining what "done" means
- Not testing the checklist with another person
- Not updating the tracker

## Quality Gate

A checklist is ready to use only when another person can understand the task, follow the steps, check the output, and record problems without needing a long explanation.
